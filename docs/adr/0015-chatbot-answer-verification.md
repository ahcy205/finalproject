# 0015. 챗봇 답은 보여 주기 전에 판단 모델(Jev)로 검증한다

- 상태: 채택
- 날짜: 2026-10-28

## 배경

학생 챗봇은 사람 확인 없이 답을 보여 준다(ADR 0011). 지금까지의 검사는 두 가지다.
- 인용 번호가 실제 근거인지
- 앞 두 문장이 "자료에 없다"로 시작하는지

두 검사를 모두 통과해도 틀린 답이 보였다. 예를 들어 "도서관 몇 시까지 해?"에 생활관 출입시간을 도서관 시간처럼 답했고, "다시 말해줘"가 그 답을 되풀이했다(ADR 0014).

## 결정

답을 보여 주기 직전에 TypeSafe Jev(판단 전용 모델, ADR 0014)에게 예/아니요 확률을 두 가지 묻는다 (`knowledge/verify.py`).

| 질문 | 통과 조건 |
|---|---|
| answers: 답이 질문에 실제로 답하는가 (근거에 없다고만 하거나 다른 내용을 말하면 아니오) | ≥ 0.5 |
| contradicts: 답에 근거와 어긋나는 내용이 있는가 (시간·숫자·점수·허용 여부·방향·대상. 인사말·이유 설명·문의 안내는 판단 안 함) | < 0.8 |

- 떨어지면 답을 숨기고 "근거를 확인하지 못했어요"와 관련 자료 링크를 보여 준다(기존 unverified와 같음).
- 새 질문의 답과, 다시 말하기·요약의 답(앞 질문으로 검증) 모두에 쓴다. 인사·감사에는 쓰지 않는다.
- 검증 결과(통과 여부, 점수, 이유)는 익명 기록 `ChatLog.verification`에 남긴다.
- **Jev를 쓸 수 없으면**(키 없음, 장애, 5초 시간 초과) 검증 없이 기존 검사만으로 보여 준다. 답을 만든 로컬 모델이 자기 답을 검증하는 것은 의미가 약해 대신 쓰지 않는다.
- **외부 전송:** 질문(개인정보 가림), 근거(공개 자료), 답이 TypeSafe로 간다. 사용자가 승인했다(2026-10-28).
- 설정: `KNOWLEDGE_VERIFIER_BACKEND` (`jev` / `none`). 키(`TYPESAFE_API_KEY`)가 없으면 `none`이다.

## 질문과 기준값을 정한 과정

### 1. 라벨을 붙인 53개로 질문 고르기

- **good 28:** 답할 수 있는 질문에 사실이 맞게 들어간 챗봇 답
- **bad_swap 11:** good 답에서 사실 하나만 바꾼 답 (시각 +1시간, 금지↔허용, 점수 +2)
- **bad_real 14:** 범위 밖 질문인데 화면에 보인 답

| 질문·기준 | good 통과 | bad_swap 거름 | bad_real 거름 |
|---|---|---|---|
| "모든 사실이 근거에 있는가" ≥ 0.3 | 19/28 | 8/11 | 8/14 |
| answers ≥ 0.5 | 27/28 | 0/11 | 14/14 |
| contradicts < 0.7 | 25/28 | 9/11 | 1/14 |
| **answers ≥ 0.5 + contradicts < 0.8** | **27/28** | **9/11** | **14/14** |

- **"모든 사실이 근거에 있는가"는 쓰지 않았다.** 너무 엄격했다. 좋은 답의 인사말·이유 설명("조용한 환경을 위해")까지 근거에 없다고 봐서 좋은 답 대부분을 떨어뜨렸다.
- **두 질문은 하는 일이 다르다.** "answers"는 범위 밖 답을 모두 잡았지만 사실을 바꾼 답은 하나도 못 잡았다. "contradicts"는 그 반대였다.
- **good인데 떨어진 답:** 셔틀 방향을 거꾸로 말한 답이었다. 라벨이 틀렸던 것이고, 떨어뜨린 판단이 옳다.
- **bad_swap인데 통과한 2개:** 의미 없는 곳(맺음말의 "확인할 수 없습니다" → "있습니다")만 바뀐 답이었다.

### 2. 새로 만든 답으로 기준값 다시 보기

처음 정한 contradicts < 0.7로 챗봇 평가(42문항)를 두 번 돌렸다. 그 결과 맞는 답까지 숨겼다(자치위원 혜택, 소등 시간). 점수를 보니 이 답들은 answers 0.68–0.88, contradicts 0.70–0.84였다. 반면 숨겨야 할 답은 모두 answers < 0.5였다. 그래서 contradicts 기준을 0.8로 올렸다.

- 0.8에서도 1단계의 bad_swap은 9/11을 잡는다. 0.85로 올리면 7/11로 떨어진다.
- 기준값을 이 두 번의 답을 보고 다시 정했으므로, 아래처럼 **새로 만든 답으로 두 번 더** 쟀다.

## 측정 (contradicts < 0.8, 새 답 두 번, exaone3.5 + Jev)

원문: `knowledge/eval/results/2026-10-28-chat-verify-{1,2}.json`

| | 검증 없음 (2026-10-27, 2회) | **검증 (2회)** |
|---|---|---|
| 범위 밖 질문 거절 | 0.80 / 0.90 | **1.00 / 1.00** |
| 답할 수 있는 질문 중 숨긴 답 (잘못 거절) | 0.03 / 0.06 | 0.19 / 0.22 |
| 시간 중앙값 | 2.8초 / 3.2초 | 3.0초 / 2.7초 |

"잘못 거절"이 늘어서 사람이 숨긴 답을 직접 읽었다. **검증으로 숨긴 9개 중 8개는 실제로 틀린 답이었다.**
- 소등 "23:00 이후" (규칙은 00:00)
- 흡연 "벌점 18점" (18은 벌점표의 행 번호)
- 금요일 석식 "오후 7시 30분~9시" (실제 17:30~19:00)
- 셔틀 방향을 거꾸로 말한 답 5개

맞는 답을 숨긴 것은 1개(책상 파손 변상)다. 검증 없이는 이 8개가 학생에게 보였다. 예전 채점은 "퇴관" 같은 단어만 있으면 맞은 것으로 쳐서, 이런 답을 맞은 것으로 셌다.

## 검토했지만 하지 않은 것: 첫 문장 검사 없애기

검증이 범위 밖 답을 잘 잡으므로, 첫 문장 검사(ADR 0011)를 없애면 그 검사가 막던 맞는 답을 되살릴 수 있는지 확인했다. 4번의 측정에서 첫 문장 검사로만 막힌 답을 검증에 넣어 보았다.

| 첫 문장 검사로 막힌 답 | 개수 | 검증 결과 |
|---|---|---|
| 범위 밖 질문 | 19 | 19개 모두 걸러짐 |
| 맞는 답 ("전기장판은 명시돼 있지 않지만 전열기는 금지 [3]" 등) | 5 | 5개 통과 → 되살아남 |
| 틀린 답 ("인원 점검은 수요일 저녁") | 3 | 3개 통과 → **틀린 답이 보이게 됨** |

학생에게 바로 가는 답에서는 "답 없음"보다 "틀린 답"이 더 나쁘다. 그래서 첫 문장 검사는 유지한다. 검증 질문이나 모델이 나아지면 다시 잰다.

## 한계

- 검증도 확률 판단이다. 기준값은 우리 질문 42개와 라벨 53개로 정했다. 익명 기록의 `verification`과 👎를 모아 계속 확인한다.
- 같은 답이라도 판단할 때마다 점수가 조금 달라진다(예: 금요일 석식 contradicts 0.64 ↔ 0.9).
- 답 하나에 Jev 호출이 한 번 더 늘었다(약 0.2초, 입력 약 2,000토큰 ≈ 0.0001달러).
